## 0. 一页人话

**结论**：这件事不需要一个"多 agent 团队"，需要的是一条**五步流水线，两道由你拍板的门**。每一步是一个边界清楚的 agent 任务，可以由不同会话、不同档次的模型接力做；两道门之外的事都不打扰你。

```text
S1 汇总 ──▶ S2 归并评估 ──▶ [门 G1 你决定进库与分层] ──▶ S3 派生任务书 ──▶ [门 G2 你授权施工] ──▶ S4 回收 ──▶ S5 反馈教训
 次一档          前沿档                                      次一档起草+前沿复核                    次一档          前沿档
```

为什么不更复杂：十份"可抽取"清单已经存在，识别工作已经做完；剩下的是合并、判断、拍板、派单、回收——这些是顺序关系，没有并行需求，也没有需要互相制衡的独立立场。为什么不更简单（一个 agent 一口气做完）：合并与判断混在一次输出里无法核对来源；拍板必须是你的；派给编码 agent 的任务书必须自包含且可验收——这三处是不同的信任边界，拆开才能各自检查。

## 1. 身份与状态

设计对象：为"从多个同构小项目的需求文档中抽取公共库能力"这项长期重复工作设计 agent 组织。版本 v0.1，候选状态，作者 claude-fable-5.1，审阅者待定（建议 GPT 侧回评一次）。

## 2. 问题与结果

- **已批准的目标**（Owner 原话 S-00、S-32、2026-08-30 消息二）：把多个项目的需求记录中的重复模式找出来，沉淀成自用公共库；为项目做设计的本质是设计一组让 agent 遵守的提示词/记录方案/文件组织。
- **成功**：每次有新项目或旧项目更新需求文档后，能以固定流程、最多两次 Owner 拍板，产出可交给编码 agent 的公共库任务，并在完成后把经验记回来。
- **失败**：又产出一份没人执行的清单；或把某个项目的偶然实现固化进公共库；或 Owner 被拉进逐条阅读。
- **非目标**：本设计不写代码、不决定公共库的具体 API、不决定公共库仓库的位置与权属边界（这些是门 G1/G2 的 Owner 决定）。

## 5. 权威与来源

- 公共库 API 的真相源 = 公共库自己仓库的文档（不是登记表）。
- 登记表、决策包、任务书 = 候选/证据/任务，不是真相。
- Meta-Agent 仓只保存方法、模板与用例指针；不保存业务内容。
- 人类专属决定：进库与分层（G1）、施工授权与仓库权属（G2）、任何"某项目规则升为通用默认"的判断。

## 6. 拓扑理由（基线阶梯）

| 基线 | 描述 | 是否足够 | 理由 |
|---|---|---|---|
| B0 手工清单 | Owner 自己读十份清单再合并 | 否 | 违反 Owner"不关心细节、不可能了解"的明示；十份清单合计数万字 |
| B1 一次性直接 agent | 一个提示："读十份文档，给出公共库方案" | 否 | 来源不可追溯（R1 失败）；判断与建议混杂；输出不可核对；把 Owner 该做的决定一并做了（R3 失败） |
| B2 强单 agent 带草稿与自检 | 一个会话分步做完 S1–S3 | 可用但不选 | 三个信任边界（机械合并 / 判断 / 面向他人的任务书）混在一个上下文，出错时无法定位；且 S1/S4 本可交次一档省额度 |
| **B3 确定性工作流 + 有界 agent 步骤 + 人类门** | 五步两门，每步自包含 | **选定** | 顺序依赖天然；每步产物可独立核对；门放在真正需要人的地方；档次分工降低成本 |
| B4 同一 agent 串行扮演多角色 | 同一模型分角色串行 | 等价于 B3 的实现方式之一 | B3 不要求不同模型，只要求步骤边界与新上下文 |
| B6/B7 多 agent 团队 | 并行多 agent 互评 | 否 | 无并行需求；唯一的"独立立场"需求（评估不自证）用"前沿复核 + Owner 门"已满足；多 agent 增加协调与权限面（反模式 #1/#14 教训） |

## 7. 角色与阶段

| 阶段 | 角色（阶段任务，不是常驻 agent） | 输入 | 输出 | 模型档 | 停止/升级条件 |
|---|---|---|---|---|---|
| S1 汇总 | 汇总员 | 各文档"可抽取"节；现有库 API 索引 | 跨项目候选登记表 v0.x（每行一条候选，带来源） | 次一档足够（机械、可核） | 某文档无该节 → 记 unknown 并停在该项，不从代码反推 |
| S2 归并评估 | 评估员 | 登记表；分层原则；不应抽取清单；权属边界 | 能力族表（合并同类）、每族建议与理由、风险标记；**决策包草案**（人话、≤10 题/批） | 前沿档 | 出现权属不明或跨库冲突 → 标记，交 G1；不自行决定 |

| S3 派生任务书 | 任务起草员 + 前沿复核 | G1 结果；复盘的流程与清单 | 每个批准族一份自包含任务书（范围、不变量、API 草图中立于项目字段、测试矩阵、消费方迁移、验收判据、冻结门、需更新的文档） | 次一档起草，前沿档复核 | 任务书无法自包含（依赖未定的库位置/权属）→ 停，回 G1 |
| **G2** | Owner | 任务书 | 授权在公共库/项目仓库施工（Meta-Agent 之外的写入） | — | — |
| S4 回收 | 汇总员 | 编码 agent 交付物、测试结果、消费方迁移记录 | 登记表状态更新（adopted/deferred/rejected）、缺陷清单 | 次一档 | 无消费方迁移证据 → 状态只能是 implemented_not_adopted |

## 9. 权限与副作用

- S1/S2/S3 只读私有需求文档，只写私有分析目录；**不写任何代码仓库**。
- 实际改公共库/项目代码的只有 G2 之后由 Owner 授权的编码 agent，遵守各项目自己的 AGENTS.md。
- Meta-Agent 公开仓零业务内容。
- 无外部服务调用；无自动化触发；所有步骤由 Owner 或其指定的会话手动启动。

## 11. 评估与假成功检查

- **S1 完整性**：每份文档的"可抽取"节逐条映射；映射计数与原节条目数对账。
- **S2 可追溯**：每族的每条来源可点开；建议与事实分开标注。
- **决策包可用性**：Owner 答题用时、追问次数（目标 0 次追问）。
- **S3 质量**：任务书过复盘 §9 十二项编码前检查。
- **假成功防线**：`adopted` 必须有消费方迁移 + 测试通过证据；实现完成但没人用 = `implemented_not_adopted`。
- **成本指标**：Owner 触碰次数；每族从 approved 到 adopted 的天数；重复代码减少量（后续测量）。

## 12. 部署假设

本地 Windows 开发环境；编码 agent 为 Codex/Claude Code 本地会话（云端不能跑 ArcObjects，见复盘）；任务书须声明 x86/STA、许可、临时 GDB 等环境前提（复盘 §5.1）。

## 13. 回退与恢复

任何阶段产物都是文件，重做即回退；登记表用 superseded_by 而非覆盖；施工阶段的回退归各代码仓库自己的规则（复盘 §4 G 冻结门失效即撤销）。
